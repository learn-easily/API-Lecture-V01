4რასაც ხედავ — და რასაც ვერ ხედავ

⏱ 2 წთ

საიტი აისბერგს ჰგავს. ზემოთ პატარა ნაწილია — ის, რასაც მომხმარებელი ხედავს. ეს არის Frontend.

→ 1 Backend (წყლის ქვეშ)

მაგრამ წყლის ქვეშ გაცილებით დიდი ნაწილია, რომელსაც ვერავინ ხედავს. ეს არის Backend.

→ 2 ზედა ნაწილის აღწერა

Frontend — ღილაკები, ფერები, ტექსტი, ფორმები. ლამაზი და ხილული.

Backend კი ინახავს მონაცემებს, ამოწმებს წესებს, ამოწმებს ვინ ხარ და რისი უფლება გაქვს, და ელაპარაკება ბანკს, ფოსტას, SMS სერვისს.

მთავარი: რასაც ეკრანზე ხედავთ, ეს საიტის მხოლოდ პატარა ნაწილია.

მარცხნივ: ანა და გიორგი, თითოეული საკუთარ კომპიუტერთან. ორივე ხედავს — მარაგში 1 ლეპტოპია.

ორივემ ერთდროულად დააჭირა „ვიყიდე“. და ორივეს ეუბნება — წარმატებით!

→ 2 პრობლემა

გაიყიდა ორი ლეპტოპი, მარაგში კი ერთი იყო. რატომ? იმიტომ, რომ ბრაუზერის კოდი თითოეულის კომპიუტერზე მუშაობს — ანას ბრაუზერმა არ იცის, რა ხდება გიორგისთან.

❓ როგორ გამოვასწოროთ? ~ (სწორი პასუხი: საჭიროა ერთი საერთო ადგილი)

სწორედ. საჭიროა ერთი საერთო ადგილი ყველასთვის — სერვერი. მარაგი ახლა ინახება იქ, ერთ ადგილას.

სერვერი ამოწმებს: მარაგი 1-ია, კარგი — ყიდის, მარაგი ხდება 0.

სამზარეულო — სადაც რეალური საქმე კეთდება. სტუმარი აქ ვერ შევა. ეს არის Backend.

11API შედგება Endpoint-ებისგან

⏱ 4 წთ · ! ერთ-ერთი მთავარი სლაიდი, ნელა

აი, რეალური API. სამი სვეტი: მარცხნივ საიტი, შუაში API, მარჯვნივ Backend-ის კოდი.

შუა სვეტს დააკვირდით. API ერთი დიდი კარი არ არის — ეს ბევრი პატარა კარია. თითოეულ კარს ჰქვია Endpoint.

თითოეულ Endpoint-ს აქვს: მეთოდი (GET, POST) + მისამართი (/api/products) + ერთი კონკრეტული მიზანი.

პირველი — პროდუქტების სია. მეორე — ერთი პროდუქტი. მესამე — შეკვეთის გაკეთება. მეოთხე — ჩემი კალათა.

→ 1 კავშირები („იძახებს“)

ყოველი Endpoint მიბმულია Backend-ში ერთ ფუნქციაზე. ეს ფუნქციები ჩვენ დავწერთ C#-ში.

→ 2 მოთხოვნა #1

საიტს პროდუქტების სია სჭირდება. აგზავნის მოთხოვნას GET /api/products-ზე. ეს Endpoint ანთდება და Backend-ში იძახებს ფუნქციას GetAllProducts().

→ 3 მოთხოვნა #2

მომხმარებელმა „შეკვეთა“ დააჭირა. საიტი აგზავნის POST /api/orders-ს — ეს უკვე სხვა კარია, და ის სხვა ფუნქციას იძახებს: CreateOrder().

→ 4 განმარტება

Endpoint = მეთოდი + მისამართი. მოთხოვნა მოდის Endpoint-ზე → Endpoint Backend-ში შესაბამის ფუნქციას ააქტიურებს.

❓ რესტორანთან დავაკავშიროთ: რა არის აქ „ხაჭაპური → თონე“? ~ (Endpoint → ფუნქცია)

ეს სლაიდი დაიმახსოვრე — პრაქტიკაში app.MapGet(...) ზუსტად ერთი ასეთი Endpoint-ია, და იქ ამ სლაიდზე მიუთითებ.

12API — სიტყვა-სიტყვით

⏱ 1 წთ

→ 1 A — Application · პროგრამა

→ 2 P — Programming · პროგრამირების

→ 3 I — Interface · ინტერფეისი, „შეხების წერტილი“

→ 4 განმარტება

API = წესები, რომლითაც ერთი პროგრამა ელაპარაკება მეორეს.

ადამიანი პროგრამას ღილაკებით ელაპარაკება — ეს UI-ა. პროგრამა სხვა პროგრამას API-ით ელაპარაკება.

17Request და Response = წერილი და პასუხი

→ 1 მეთოდი

მეთოდი: რა გვინდა? მაგალითად GET — „მომეცი“.

→ 2 მისამართი

მისამართი: რისი? /api/products.

→ 3 მონაცემი

მონაცემი — თუ რამე ახალს ვაგზავნით, მაგალითად ახალი პროდუქტი. GET-ს ეს არ სჭირდება.

→ 4 სტატუსი

→ 5 მონაცემი

და თავად მონაცემი — პროდუქტების სია.

→ 6 მაგალითი ერთ ხაზზე

აი, ასე გამოიყურება რეალურად: მარცხნივ მოთხოვნა, მარჯვნივ პასუხი.

ყოველ Request-ს ყოველთვის ერთი Response აქვს.

19პასუხის „შუქნიშანი“ 🚦
