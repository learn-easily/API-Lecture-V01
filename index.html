02
API = მიმტანი

შეკვეთა მიდის — კერძი მოდის

სტუმარმა არ იცის, როგორ მზადდება კერძი — და არც სჭირდება.
სამზარეულო არ იცნობს სტუმარს — მხოლოდ შეკვეთას ხედავს.
მიმტანი ორ მხარეს აკავშირებს და ორივეს „საიდუმლოებს“ იცავს. Frontend-ს არ აინტერესებს რა ბაზაა ან რა ენაზეა Backend დაწერილი — მხოლოდ შეკვეთა და პასუხი.
მიმტანმა იცის, ვის მიუტანოს

ყოველ შეკვეთას — თავისი მზარეული

მიმტანი თვითონ არ ამზადებს — ის სწორ ადგილას მიაქვს შეკვეთა. API-შიც ასეა: ყოველ მოთხოვნას თავისი ადგილი აქვს.
მიმტანი იღებს სხვადასხვა შეკვეთას და თითოეული სხვადასხვა ადგილას მიაქვს: ხაჭაპური — თონესთან, სალათი — ცივი კერძების მზარეულთან, ანგარიში — სალაროში. შემდეგ სლაიდზე იგივეს ვნახავთ რეალურ API-ში.
Endpoint

API შედგება Endpoint-ებისგან

Endpoint = მეთოდი + მისამართი ერთი კონკრეტული მიზნით. მოთხოვნა მოდის Endpoint-ზე → Endpoint Backend-ში შესაბამის ფუნქციას ააქტიურებს.
API ერთი დიდი „კარი“ არ არის — ეს ბევრი პატარა კარის ნაკრებია. თითოეულ კარს (Endpoint-ს) თავისი მისამართი და თავისი საქმე აქვს. Frontend-მა იცის რომელ კარზე დააკაკუნოს, კარი კი Backend-ში სწორ ფუნქციას „ურეკავს“. პრაქტიკაში app.MapGet(...) = ზუსტად ერთი Endpoint.

ერთი Backend — ბევრი კლიენტი

მაგალითი: ბანკის საიტი და ბანკის მობილური აპი ერთსა და იმავე API-ს ელაპარაკება. ამიტომ ბალანსი ორივეგან ერთნაირია. ამინდის აპები ამინდის სერვისის API-ს იყენებენ; „Google-ით შესვლა“ Google-ის API-ა.
